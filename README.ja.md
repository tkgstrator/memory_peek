# memory_peek

[English](README.md)

`memory_peek` は、既にアタッチされている `dmnt:cht` セッションを通じて、現在実行中のゲームプロセスのメモリを安全に読み取るための専用 Atmosphère sysmodule です。

TCP ポート 6000 で待機し、sys-botbase と互換性のあるシンプルなテキストコマンド方式（改行で区切られた 1 行 1 コマンド形式）を採用しています。NXCTF などの既存ツールからそのまま接続できますが、メモリ書き込み、コントローラー入力の偽装、プロセスのフリーズ、ファイルシステム操作といった余計な機能は一切含まず、メモリの読み取りに必要な最小限の命令のみを提供します。使用する `dmnt:cht` IPC 要求は、`HasCheatProcess`、`GetCheatProcessMetadata`、`ReadCheatProcessMemory` の 3 種類のみです。

**ステータス:** クロスコンパイルおよび静的監査（audit）のみ完了しています。実機での Switch 起動、Atmosphère 1.12.1 ランタイム環境、LAN 通信、実際のゲーム内メモリ読み取りは未テストです。対象の SD カードのインベントリ確認、仮の Program ID の衝突チェック、および直接のリカバリ手順の準備が完了するまで、実機へのデプロイを行わないでください。SD カード上に NSP ファイルを配置しただけでは、起動やゲームのメモリ読み取りができることの証明にはなりません。

本モジュールは、実行中のゲームに対して自らデバッガ等のアタッチを行うことはありません。Atmosphère の `dmnt` チートマネージャーが対象ゲームのアクティブなセッションを既に保持している場合にのみメモリを読み取ることができます。`atmosphere/contents/<16進数16桁のTitleID>/cheats/<16進数16桁のBuildIDプレフィックス>.txt` に空のチートファイルを配置することで、チートコード（opcode）を実行することなく、ゲーム起動時にこのセッションを確立させることができます。ファイル名には、[Atmosphère 1.12.1 のドキュメント](https://github.com/Atmosphere-NX/Atmosphere/blob/1.12.1/docs/features/cheats.md)に記載されているとおり、メイン NSO のビルド ID の**先頭 8 バイト**（16 進数 16 桁）を使用します。ファイルを配置する前に、実行対象の正確なゲームおよびビルドからこのプレフィックスを確認してください。未検証のバイナリや別バージョンのゲームから推測してはなりません。また、Atmosphère は起動時にチート有効化キーを判定します（デフォルト: **L ボタンを押していない場合に有効**）。L ボタンを押したまま起動するとチートのロードが抑止され、空のチートファイルが存在していてもリーダーが利用不可になります。セッションが利用できない場合、モジュールはゲームにアタッチしたりゲームを停止させたりすることなく、`ERR READER_UNAVAILABLE` を返します。この仕組みの実機における起動時動作はまだ未検証です。

## コマンド仕様・プロトコル

コマンドは、改行（LF または CRLF）で区切られた 1 行のプレーンテキスト（ASCII）として送信します。応答も同様に CRLF で区切られた 1 行のテキストとして返されます。プログラムからの利用はもちろん、ターミナルから `nc`（netcat）などで直接コマンドを手入力してテストすることも可能です。

サーバーは一度に 1 つのクライアント接続のみを処理し、無通信（アイドル）状態が 5 秒続くと自動的に切断します。`getVersion` はプロトコルバージョン `1.0.0` を返し、`getIdentity` はモジュール識別子 `memory_peek/1` を返します。

| コマンド | 応答 |
| --- | --- |
| `getTitleID` | 大文字の 16 進数 16 桁（Title ID） |
| `getMainNsoBase` | 大文字の 16 進数 16 桁（Main NSO ベースアドレス） |
| `getBuildID` | ビルド ID の先頭 8 バイト（大文字の 16 進数 16 桁） |
| `getHeapBase` | 大文字の 16 進数 16 桁（ヒープベースアドレス） |
| `isProgramRunning 0x<TITLE_ID>` | 指定したタイトルが現在実行中かどうかに応じて `1` または `0` |
| `peekMain 0x<OFFSET> 0x<LENGTH>` | Main NSO ベース + オフセットからの大文字 16 進数バイト列 |
| `peekAbsolute 0x<ADDRESS> 0x<LENGTH>` | 絶対仮想メモリ空間アドレスからの大文字 16 進数バイト列 |
| `peekAbsoluteMulti 0x<ADDRESS> 0x<LENGTH> ...` | 要求順に連結された大文字 16 進数バイト列 |

各行は最大 2,048 バイトに制限されており、メモリ読み取り要求は 1 リクエストあたり最大 32 範囲かつ合計 1 MiB までに制限されています。数値引数は 10 進数または `0x` プレフィックス付きの 16 進数を受け付けます。不正な形式や未定義のコマンドに対しては `ERR INVALID_REQUEST` を返します。対象ゲームが存在しない場合は `ERR NO_GAME`、読み取り失敗時は `ERR READ_FAILED`、読み取り中のゲーム切り替え検知時は `ERR GAME_CHANGED` をそれぞれ返します。`dmnt` セッションが確立されていない場合は `ERR READER_UNAVAILABLE` を返します。

メモリ読み取りは、成功応答のバイト列を送信する前に全体がバッファリングされます。認証や暗号化の仕組みはありません。サービス稼働中は、同一ネットワークから接続可能なすべてのクライアントがゲームメモリの読み取りを要求できます。

## ビルドと検証

ホスト側の単体テストの実行には、C コンパイラと Python 3 が必要です:

```sh
make test
```

ピン留めされローカルにキャッシュされた devkitPro の Docker イメージを使用して、クロスコンパイルと監査を実施できます。これは静的ビルドで使用されているイメージダイジェストと同一です:

```sh
docker run --rm --user "$(id -u):$(id -g)" -v "$PWD":/work -w /work \
  devkitpro/devkita64@sha256:1fc388c3a0d34bd2045a6dadcb1020e069d5f876a187fd705de14b4440c00282 \
  make switch
```

ビルド成果物は `build/switch/memory_peek.elf`、`.nso`, `.npdm`、および `.nsp` です。現在のハッシュ値および検証結果は `BUILD-MANIFEST.md`（または `BUILD-MANIFEST.ja.md`）に記録されています。

`make switch` は `hactool` を使用して生成された NPDM 権限を抽出し、厳格なシステムコール（SVC）およびサービス接続のホワイトリストを照合し、ファイルシステム権限がゼロであることを確認し、禁止 API や未許可の SVC がないかソースコードと ELF シンボルをスキャンします。また、監査対象となった NPDM と NSO が NSP 内に含まれる正確な 2 つの構成要素であることを確認します。監査では、直接のデバッグアタッチ/読み取り/書き込み SVC（`0x60`/`0x6A`/`0x6B`）、対象プロセスの変更機能、追加のカーネル機能カテゴリ、およびソースコード内の書き込み系やアタッチ系の `dmnt:cht` 呼び出しをすべて拒否します。これらは静的検証であり、実機ランタイム環境での互換性や通信の秘匿性を保証するものではありません。

仮の Program ID は `0x43004D5045454B01` です。インストール前に対象の SD カード上で未使用であることを確認してください。本プロジェクトにはインストーラーは含まれておらず、SD カードの自動変更も行いません。実機のインベントリ確認、ロールバックの準備、実際の起動およびメモリ読み取りの検証は別個のデプロイメントゲートとなっており、`docs/superpowers/specs/2026-10-31-memory-peek-design.md` に記載されています。

## CIとリリース

[`integration.yaml`](.github/workflows/integration.yaml) は、`master` ブランチへのプッシュおよびプルリクエスト時に、ホストテストの実行、Switch 向けの新規クロスコンパイル、および成果物の権限監査を実行します。また、監査済みの NSP と生成された `SHA256SUMS` をワークフロー成果物としてアップロードします。

[`deployment.yaml`](.github/workflows/deployment.yaml) は、`master` ブランチ上のコミットに対する `vX.Y.Z` タグのプッシュによってトリガーされます。同一の統合チェックを実行し、転送された NSP のチェックサムを検証したうえで、NSP と `SHA256SUMS` を GitHub Releases に公開します。既存のリリースに対して同じタグを再実行した場合は、アセットを上書きせずにエラー終了します。リリースのバージョン番号は、通信プロトコルのバージョンを示す `getVersion` とは独立しています。このワークフローは GitHub へのビルド成果物の公開のみを行い、Switch へのインストールや上記の実機検証を代替するものではありません。
